2.1 ¿Qué es un Proceso?

"Conceptualmente, cada proceso tiene su propia CPU virtual. En la realidad, la CPU física alterna entre procesos — esto se denomina multiprogramación."
— Tanenbaum & Bos
ConceptoNaturalezaAnalogía
ProgramaEntidad estática (código en disco)La receta de cocina
ProcesoEntidad dinámica (programa + estado)La actividad de cocinar
  • Un mismo programa puede dar lugar a múltiples procesos simultáneamente.
  • La traza de un proceso es la secuencia de instrucciones ejecutadas.
  • El dispatcher es el módulo del SO que alterna el procesador entre procesos.

2.2 El Modelo de Proceso

En un sistema con una sola CPU, en cualquier instante solo un proceso ejecuta físicamente. La conmutación rápida crea la ilusión de paralelismo — pseudoparalelismo.

Cada proceso tiene:

  • Contador de programa (PC) privado
  • Registros propios
  • Pila (stack) propia
  • Espacio de memoria propio
sequenceDiagram participant A as Proceso A participant B as Proceso B participant C as Proceso C activate A Note over A: CPU deactivate A activate B Note over B: CPU deactivate B activate C Note over C: CPU deactivate C activate A Note over A: CPU deactivate A

2.3.1 Modelo de Dos Estados

EstadoDescripción
RunningUsando la CPU ahora
Not RunningEspera su turno en una cola

Limitación: no distingue entre procesos que esperan E/S (bloqueados, no pueden ejecutar) y procesos listos (pueden ejecutar). Esto lleva al modelo de cinco estados.

2.3.3 Modelo de Cinco Estados

EstadoDescripción
NewRecién creado; aún no listo
ReadyListo; esperando CPU
RunningEjecutando en CPU
BlockedEsperando E/S o evento
ExitTerminado o abortado

2.3.4 Procesos Suspendidos

Problema: si todos los procesos están bloqueados, la CPU queda ociosa.
Solución — Swapping: mover procesos al disco para liberar memoria.

EstadoDescripción
Ready/SuspendEn disco, listo para ejecutar
Blocked/SuspendEn disco y esperando evento

Razones para suspender

  • Swapping — liberar memoria
  • Solicitud del usuario (depuración)
  • Temporización periódica
  • Solicitud del proceso padre

2.4.1 Tablas del Sistema Operativo

Para gestionar recursos, el SO mantiene cuatro categorías de tablas:

TablaContenido

I/OEstado de dispositivos; operaciones E/S en curso

2.4.2 La Imagen del Proceso

La imagen del proceso es la colección completa de información que define a un proceso:

ElementoDescripción
User ProgramEl código ejecutable del programa
User DataDatos del programa, variables globales, pila de usuario
StackPila LIFO para llamadas a procedimientos
PCBDatos que el SO necesita para controlar el proceso

2.4.3 Bloque de Control del Proceso (PCB)

"El PCB define el estado del SO. Un error en un módulo podría corromper los PCBs de múltiples procesos." — Stallings

Identificación

  • PID — ID único del proceso
  • PPID — ID del proceso padre
  • UID / GID — Usuario y grupo

Estado del Procesador

  • Registros de propósito general
  • Contador de programa (PC)
  • Punteros de pila (SP)
  • PSW / EFLAGS

Control del Proceso

  • Estado actual
  • Prioridad
  • Gestión de memoria
  • Archivos abiertos

2.6 Creación de Procesos

Eventos que originan un proceso

EventoDescripción
Inicialización del sistemaSO crea procesos y daemons al arrancar
Llamada al sistemaUn proceso crea un hijo
Petición del usuarioDoble clic o comando en terminal
Trabajo batchSO lanza trabajo de la cola batch

UNIX — fork()

  • Crea un clon del proceso padre
  • Padre recibe PID del hijo; hijo recibe 0
  • Uso de execve() para cambiar la imagen
  • Copy-on-write: memoria compartida hasta que alguno escribe

Windows — CreateProcess()

  • Fusiona creación e imagen en una sola llamada
  • Sin herencia de jerarquía explícita

2.7 Terminación de Procesos

TipoVoluntarioCausa
Salida normalSíTerminó su trabajo → exit()
Salida por errorSíDetecta error fatal y se termina
Error fatalNoDivisión por cero, segfault, instrucción ilegal
EliminadoNoOtro proceso ejecuta kill() o TerminateProcess()

En la mayoría de los sistemas, solo el proceso padre puede matar a sus hijos.

2.8 Jerarquías de Procesos

UNIX — Árbol estricto

  • init (PID 1) es la raíz
  • Relación padre-hijo permanente
  • Grupos de procesos
graph TD A["init (PID 1)"] A --> B[sshd] B --> C[bash] C --> D[vim] A --> E[cron] A --> F[httpd] F --> G[worker_1] F --> H[worker_2]

Windows — Sin jerarquía

  • Todos los procesos son iguales
  • El padre recibe un handle del hijo
  • El handle puede transferirse — rompe cualquier jerarquía

2.9.3 Pasos de una Conmutación

  1. Guardar el contexto del procesador (PC + registros del proceso actual)
  2. Actualizar el PCB del proceso actual (estado: Ready/Blocked/Exit)
  3. Mover el PCB a la cola apropiada
  4. Seleccionar otro proceso — función del scheduler
  5. Actualizar el PCB del proceso seleccionado (estado → Running)
  6. Actualizar estructuras de gestión de memoria (tablas de páginas)
  7. Restaurar el contexto del proceso seleccionado
La conmutación tiene un costo real en tiempo de CPU: el tiempo invertido no realiza trabajo útil.

2.10 Threads — ¿Por qué usarlos?

Un thread (hilo) es una unidad de ejecución dentro de un proceso. Comparte memoria y recursos con otros threads del mismo proceso.

RazónExplicación
ParalelismoActividades paralelas en una aplicación
Eficiencia100× más rápidos de crear que procesos
E/S + CPUUn thread espera E/S; otro sigue con la CPU
MulticoreAprovechan paralelismo real

2.10.2 Modelo Clásico de Threads

Compartido (por proceso)

  • Espacio de direcciones
  • Variables globales
  • Archivos abiertos
  • Procesos hijos
  • Señales y manejadores

Privado (por thread)

  • Contador de programa (PC)
  • Registros
  • Pila (stack)
  • Estado (Running/Ready/Blocked)
Los threads no tienen estado Suspended porque la memoria es compartida — no aplica swapping individual por thread.

2.10.3 / 2.10.4 — ULT vs. KLT

ULT — Espacio de usuario

El kernel solo ve procesos de un solo thread. Los threads los gestiona una biblioteca.

VentajasDesventajas
Conmutación sin syscall (rápido)Syscall bloqueante bloquea todo el proceso
Algoritmo de planificación propioNo libera CPU sin llamar a la biblioteca

KLT — Kernel

El kernel conoce y gestiona los threads directamente.

VentajasDesventajas
Thread bloqueado → kernel planifica otro del mismo procesoMayor overhead por syscalls
Paralelismo real en multicore

Híbrido: múltiples threads de usuario por thread de kernel.

2.11 Procesos en UNIX SVR4

UNIX SVR4 define 9 estados de proceso:

EstadoDescripción
User RunningEjecutando en modo usuario
Kernel RunningEjecutando en modo kernel
Ready to Run, in MemoryListo; en memoria principal
Asleep in MemoryBloqueado; en memoria principal
Ready to Run, SwappedListo; en disco
Sleeping, SwappedBloqueado; en disco
PreemptedDesalojado al volver de kernel a usuario
CreatedRecién creado por fork()
ZombieTerminado; espera que el padre lo recoja
Un proceso en modo kernel NO puede ser desalojado — esto hace a UNIX tradicional inadecuado para tiempo real estricto.
